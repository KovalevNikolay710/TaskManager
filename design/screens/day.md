# Задачи на день

Макет: `design/screens/day.html`. Панель в правом верхнем углу переключает состояния макета: данные, есть свободное время, много задач, плана нет, план пуст, загрузка, ошибка, окно «Изменить план», тему. Во фронтенд панель не переносить. Наведите курсор на сектор или задачу (или нажмите на сектор): так видна связь «сектор ↔ задача».
Компоненты и форматы описаны в `design/system.md`, значения берутся из `design/tokens.css`, эталонная вёрстка — `design/components.css`.

## Назначение
Пользователь указывает, сколько времени у него есть сегодня. Приложение делит это время между **всеми** активными делами: и обязательными, и приятными (хобби тоже заводятся задачами). Сколько получит каждая задача, зависит от приоритета `Pt` и от того, какой темп нужен, чтобы успеть к сроку. Кольцевая диаграмма показывает, какую часть дня занимает каждая задача. Это стартовый экран приложения: открыл, увидел, на что сколько времени отдать, отметил сделанное.

## Как делится время (коротко, для интерфейса)
- Каждая задача в плане получает **не меньше 0:15**.
- Сначала каждая задача получает «темп»: оставшуюся работу, поделённую на число дней до дедлайна. Если времени дня не хватает даже на это, время делится пропорционально `Pt`. Если остаётся лишнее, оно тоже раздаётся пропорционально `Pt`, но задача не получает больше, чем ей осталось сделать. Что не раздалось — сектор «Свободно».
- План фиксируется в момент составления. Отметка «выполнено» не перераспределяет время: сектор задачи остаётся на месте и становится серым. Перераспределить время можно кнопкой «Пересобрать план».
- Точный алгоритм для бэкенда — в разделе «Требуется от бэкенда», п. 2.

## Данные

`userId = 1` — константа фронтенда (`VITE_USER_ID`).
Маршрут: `/day` (сегодня) и `/day?date=YYYY-MM-DD`. Корень `/` ведёт на `/day`.

Загрузка — три параллельных запроса:
1. `GET /api/days/user/1` → `Day[]` с вложенными `Tasks` и (новое) `Slots`. Текущий день ищется на клиенте: локальная дата `Day.Date` совпадает с выбранной; если таких дней несколько, берётся день с наибольшим `DayId`.
2. `GET /api/groups/user/1` → `Group[]`, только для подписи группы у задачи. Ошибка этого запроса не ломает экран: задачи просто показываются без подписей групп.
3. `POST /api/tasks/user/1`, тело `{}` → `Task[]` (кэш `queryKeys.tasks`, общий с «Все задачи»). Нужен только для подсказки «Ещё N активных задач не в плане». Если запрос упал, подсказка не показывается.

`GET /api/days/:id` не используется.

| Что показываем | Источник | Поле ответа | Формат |
|---|---|---|---|
| Дата в `DateSwitcher` | `GET /api/days/user/:user_id` | `Day.Date` | «Сегодня, 24 сентября»; под датой день недели, если это не сегодня, вчера или завтра |
| Подзаголовок | вычисляется | `Day.Tasks[].Status` | «Выполнено 1 из 7» |
| Время на день (100% кольца) | то же | `Day.TimeForTasks` (минуты) | `Ч:ММ`, «6:00» |
| Сектор задачи | то же | `Day.Slots[]`: `TaskId`, `Minutes` | угол = `Minutes / TimeForTasks × 360°` |
| Цвет сектора | то же | `Task.GroupPriorty` (вес группы, берётся из задачи с тем же `TaskId`) | `--color-weight-{N}`, N ограничивается 1–10; у задачи без группы вес 1. У выполненной задачи (`Status = 2`) — `--color-day-done` |
| Сектор «Свободно» | вычисляется | `TimeForTasks − Σ Slots[].Minutes` | показывается, если остаток ≥ 5 мин; цвет `--color-day-free` (совпадает с треком кольца) |
| Центр кольца (по умолчанию) | вычисляется | `Σ Minutes` по слотам активных задач | крупно «4:30», под ним «осталось из 6:00» |
| Сводка под кольцом | вычисляется | слоты | «В работе: 6 задач — 4:30»; «Выполнено: 1 — 1:30» (если есть выполненные); «Свободно — 2:55» (если ≥ 5 мин); «Приоритет дня (осталось) — 26,9» |
| Приоритет дня (осталось) | вычисляется на клиенте | `Σ Task.Priority` задач со `Status = 1` | «26,9»; `title="Сумма приоритетов невыполненных задач плана"` |
| «Сегодня» у задачи | `Day.Slots` | `Minutes` по `TaskId` | справа от названия: **«1:25»** + «сегодня» |
| Полное время задачи | `Day.Tasks` | `Task.TimeForExecution` | в мета-строке: «всего 3:00» |
| Название, группа, дедлайн, прогресс, приоритет | `Day.Tasks` + группы | `Name`, `GroupId`→`Group.Name`, `DeadLine`, `PercentOfCompleting`, `Priority` | как в `TaskRow`. Уровень приоритета считается относительно максимума среди активных задач **этого дня** |
| Порядок (и секторов, и списка) | вычисляется | `Status`, `Priority`, `Minutes` | сначала активные по `Priority` ↓, затем выполненные по `Minutes` ↓, затем «Свободно». Сектора идут от 12 часов по часовой стрелке в том же порядке, что и список |
| «Ещё N активных задач не в плане» | `POST /api/tasks/user/1` | задачи со `Status = 1`, `DeadLine` позже начала выбранного дня, `TaskId` которых нет в `Slots` | только для сегодняшнего и будущих дней, если N > 0 |

Если у дня нет `Slots` или у всех слотов `Minutes = 0` (план составлен до этой версии), показываем состояние «Старый план».

### Много мелких секторов
- Минимальный слот — 15 мин. При максимальном времени дня 16:00 это 5,6° дуги, при 3:00 — 30°. Сектор всегда различим: между секторами есть зазор 2px цвета `--color-surface`.
- На кольце нет текстовых подписей: при 10+ секторах они бы не поместились. Подписью служит список под кольцом, а подробности показывает центр кольца при наведении или тапе.
- У соседних задач одной группы одинаковый цвет, их разделяет только зазор. Это нормально: цвет означает **вес**, а не конкретную задачу.

### Связь «сектор ↔ задача»
- Наведение (десктоп) на сектор или строку списка: остальные сектора и строки приглушаются (opacity 0.3 и 0.45), выбранный сектор немного увеличивается (`scale(1.04)`), у строки появляется обводка 2px цвета сектора. В центре кольца: название задачи (до 2 строк), выделенное время «1:25», подпись «сегодня · Учёба» или «выполнено». Для «Свободно» — «2:55 / свободно».
- Тап по сектору (мобильный) закрепляет подсветку. Повторный тап по тому же сектору или тап вне кольца снимает её. Список при этом не прокручивается.
- Фокус клавиатуры на строке задачи тоже подсвечивает её сектор.
- Центр кольца — `aria-live="polite"`. Секторы не фокусируются: для скринридера у SVG есть `role="img"` и `aria-label` со всем планом («План на 6:00: Подготовить отчёт по ТИПИС 1 час 25 минут; …; свободно 2 часа 55 минут»), а полноценная замена диаграммы — это список.
- При `prefers-reduced-motion` сектор не увеличивается, остаётся только смена прозрачности.

## Требуется от бэкенда

### 1. `amountOfTasks` больше не нужен (блокер)
- `DayCreateRequest.AmountOfTasks` сейчас с `binding:"required"`. Фронт это поле больше не отправляет, поэтому без правки `POST /api/days/` вернёт 400. Убрать поле из `DayCreateRequest` и `DayUpdateRequest`.
- `Day.AmountOfTasks`: при сборке плана записывать туда `len(Slots)`, чтобы колонка не врала, либо удалить колонку миграцией. Фронт поле не читает.
- `TimeForTasks`: валидация `binding:"required,min=15,max=960"` (0:15–16:00) в `DayCreateRequest` и `omitempty,min=15,max=960` в `DayUpdateRequest`.

### 2. Алгоритм распределения времени «Темп + остаток»
Заменяет в `FillDayTaskListAndCalculatePriorty` отбор первых `AmountOfTasks` задач.

**Вход:**
- `T` — `Day.TimeForTasks`, минуты. При пересборке — `T − Σ Minutes выполненных слотов` (см. п. 4).
- Кандидаты — задачи пользователя со `Status = 1` и `DeadLine` позже начала дня `Day.Date` (как сейчас в фильтре). Перед расчётом у каждого кандидата пересчитать `NumberOfHoursUntilDL` и `Priority` от текущего момента (`refreshTaskPriorty(task, now)`), чтобы `Pt` был актуальным. Сохранять задачи при этом не обязательно.
- Константы: `Q = 15` — минимальный слот, `STEP = 5` — шаг округления.

**Для каждого кандидата `i`:**
- `W = Te × (100 − %) / 100` — оставшаяся работа, мин (`Te` = `TimeForExecution`, `%` = `PercentOfCompleting`);
- `D = max(1, ceil(H / 24))` — дней до дедлайна, где `H` — часы от `max(now, начало дня плана)` до `DeadLine`. Для плана на сегодня `H` = `NumberOfHoursUntilDL`;
- `need = W / D` — нужный темп, мин в день;
- `cap = max(Q, roundUp5(W))` — больше этого задаче не даём никогда;
- `base = min(max(Q, roundUp5(need)), cap)` — сколько задача получает в первую очередь.

**Решение по «если W < 15»:** задача всё равно получает 15 мин (`cap = max(Q, …)`). Минимальный слот — это минимальный отрезок внимания. Если задача закончится раньше, остаток пользователь потратит на следующую. Слотов меньше 15 мин не бывает.

**Шаги:**
1. Отсортировать кандидатов по `Pt` ↓. При равенстве раньше идёт задача с более ранним `DeadLine`, затем с меньшим `TaskId`.
2. Если `Q × n > T`, в план берутся первые `k = floor(T / Q)` кандидатов, остальные в план не попадают. Дальше работаем с `k` задачами. Если `k = 0`, план пуст.
3. `S = Σ base`.
4. **Не хватает (`S > T`):** найти `λ ≥ 0`, при котором `Σ clamp(λ × Pt_i, Q, base_i) = T`, и назначить `x_i = clamp(λ × Pt_i, Q, base_i)`. Функция монотонна по `λ`, решение существует, потому что `Q × k ≤ T < S`. Находится бинарным поиском (60 итераций хватает) или сортировкой точек излома. Потолок у каждой задачи здесь — `base`.
5. **Хватает (`S ≤ T`):** если `Σ cap ≤ T`, то `x_i = cap_i`, а остаток `T − Σ cap` — «Свободно». Иначе найти `λ ≥ 0`, при котором `Σ min(base_i + λ × Pt_i, cap_i) = T`, и назначить `x_i = min(base_i + λ × Pt_i, cap_i)` (water-filling: остаток задач, упёршихся в `cap`, автоматически переходит к остальным). Потолок у каждой задачи здесь — `cap`.
6. **Округление до 5 минут** методом наибольших остатков: `a_i = floor(x_i / 5) × 5`, затем `L = T − Σ a_i`. Пока `L ≥ 5`, прибавлять по 5 мин задачам с наибольшей дробной частью `x_i − a_i` (при равенстве — по `Pt` ↓), не превышая потолок шага 4 или 5 и не больше одного раза на задачу. В результате каждое `a_i ≥ 15`, кратно 5 и `Σ a_i ≤ T`. Остаток `T − Σ a_i` (включая 1–4 мин, если `T` не кратно 5) — свободное время. Оно не хранится, фронт считает его сам.
7. Сохранить `(DayId, TaskId, Minutes = a_i)` для каждой задачи плана.

**Пример 1 — хватает времени.** 24 сентября, 08:00, `T = 6:00 = 360`.

| Задача | Pg | Te | % | H | Pt | W | D | need | base | cap | x | **Minutes** |
|---|---|---|---|---|---|---|---|---|---|---|---|---|
| Код-ревью задачи по API | 2 | 90 | 0 | 10 | 18,0 | 90 | 1 | 90 | 90 | 90 | 90,0 | **90** |
| Подготовить отчёт по ТИПИС | 3 | 180 | 40 | 26 | 12,5 | 108 | 2 | 54 | 55 | 110 | 84,1 | **85** |
| Лабораторная №4 по БД | 3 | 120 | 0 | 74 | 4,9 | 120 | 4 | 30 | 30 | 120 | 41,4 | **40** |
| Пробежка 5 км | 1 | 45 | 0 | 14 | 3,2 | 45 | 1 | 45 | 45 | 45 | 45,0 | **45** |

| Купить продукты на неделю | 1 | 60 | 0 | 36 | 1,7 | 60 | 2 | 30 | 30 | 60 | 33,9 | **35** |
| Прочитать главу «Чистой архитектуры» | 2 | 240 | 50 | 144 | 1,7 | 120 | 6 | 20 | 20 | 120 | 23,9 | **25** |

`S = 305 ≤ 360`, `Σ cap = 1025 > 360`, значит работает шаг 5. Лишние 55 мин делятся пропорционально `Pt` между задачами, которые ещё не упёрлись в `cap` (код-ревью и пробежка уже на потолке): `λ ≈ 2,34`. Округление: `floor` даёт 80+40+90+30+40+45+20 = 345. Остаток 15 мин уходит +5 задачам с наибольшими дробными частями: отчёт (4,1), продукты (3,9) и «Чистая архитектура» (3,9). Итого 360, свободного времени нет. Это данные макета «Данные».

**Пример 2 — не хватает.** Те же задачи, `T = 4:00 = 240`. `S = 305 > 240` → шаг 4, `λ ≈ 5,95`:
код-ревью `min(107, 90)` = 90 → **90**; отчёт `min(74, 55)` = 55 → **55**; лабораторная 28,9 → **30**; пробежка 19,1 → **20**; гитара 17,0 → **15**; продукты `max(9,9; 15)` → **15**; «Чистая архитектура» → **15**. Сумма 240. Пробежка с дедлайном сегодня получает меньше своего темпа (20 из 45): её `Pt` ниже, чем у лабораторной. Так работает выбранное правило: при нехватке времени решает `Pt`.

**Пример 3 — задачи не помещаются.** Те же задачи, `T = 1:30 = 90`. `15 × 7 = 105 > 90` → `k = 6`. Не входит «Чистая архитектура» (`Pt` 1,7 равен `Pt` продуктов, но дедлайн позже). Шесть задач по **15**.

**Пример 4 — свободное время.** Код-ревью, отчёт, пробежка, продукты; `T = 8:00 = 480`. `Σ cap = 90 + 110 + 45 + 60 = 305 ≤ 480`. Все получают `cap`, свободно 175 мин = 2:55 (макет «Есть свободное»).

### 3. Где хранятся минуты и как они приходят в ответе
**Хранение.** Своя join-модель для `day_tasks` с колонкой минут:

```go
// DayTask — задача в плане дня и выделенное ей время.
type DayTask struct {
	DayId   int64 `gorm:"primaryKey"`
	TaskId  int64 `gorm:"primaryKey"`
	Minutes int   `gorm:"not null;default:0"` // выделено на этот день, минуты
}
```
Подключается через `db.SetupJoinTable(&models.Day{}, "Tasks", &models.DayTask{})` до `AutoMigrate`. Существующие строки получат `Minutes = 0`: фронт покажет для них состояние «Старый план».

**В ответе** — отдельный массив у дня:

```go
type Day struct {
	// ...прежние поля...
	Tasks []*Task   `gorm:"many2many:day_tasks;..."`
	Slots []DayTask `gorm:"foreignKey:DayId"` // та же таблица day_tasks
}
```
JSON (без json-тегов, имена как есть): `"Slots": [{"DayId": 7, "TaskId": 12, "Minutes": 85}, ...]`. Отдаётся в `POST /api/days/`, `POST /api/days/update/:id`, `GET /api/days/user/:user_id`, `GET /api/days/:id` (preload `Slots` рядом с `Tasks`).

**Почему `Day.Slots`, а не поле у `Task`:**
- минуты принадлежат паре «день + задача»: одна задача может быть в планах нескольких дней с разным временем. У `Task` такое поле было бы вычисляемым (`gorm:"-"`) и имело бы смысл только внутри ответа дня, а в `GET /api/tasks/...` было бы всегда 0 и путало бы;
- изменение аддитивное: `Day.Tasks` не меняется, старый фронт продолжит работать;
- фронт соединяет `Slots` и `Tasks` по `TaskId` за O(n).

### 4. Пересборка сохраняет выполненное
`POST /api/days/update/:id`:
1. Слоты плана, у задач которых сейчас `Status = 2`, остаются с прежними `Minutes`.
2. `R = T − Σ Minutes` этих слотов. Если `T` меньше суммы — 400 `{"error": "Время дня меньше уже выполненного (1:30)"}` (сумму в `Ч:ММ`).
3. Алгоритм из п. 2 запускается с `T = R` по кандидатам: активные задачи, включая бывшие в плане, новые и возвращённые в работу. Если `R < 15`, активных слотов нет.
4. Слоты активных задач заменяются в одной транзакции (сейчас `ReplaceTasks`, в новой версии — удаление и вставка строк `DayTask`).

Пример: из плана примера 1 выполнено «Код-ревью» (90), пользователь пересобирает с `T = 7:00`. Тогда `R = 330`, и шесть активных задач получают 110 / 55 / 45 / 50 / 40 / 30. Код-ревью остаётся с 90.

### 5. План фиксирован между пересборками
- Отметка, снятие отметки и изменение задачи **не** меняют `Minutes`.
- Удаление задачи удаляет её слот (каскад по `day_tasks` уже есть), время становится свободным.
- `GET /api/days/:id` должен отдавать сохранённый план. Сейчас `GetDayByIDHandler` вызывает `FillDayTaskListAndCalculatePriorty` и пересобирает план «на лету» при каждом чтении; после этого изменения ответ перестал бы совпадать со `Slots`.

### 6. Прежние пункты, которые остаются в силе
- **День по дате**: `GET /api/days/user/:user_id?date=YYYY-MM-DD` вместо выбора из полного списка на клиенте. Запретить второй `Day` на ту же дату (409).
- **`Day.Status`** не выставляется. Либо проставлять его, либо удалить поле; фронт определяет «Прошедший день» по дате.
- **`PriorityOfTheDay`** — сумма `Priority` невыполненных задач плана, считается при выдаче (так уже сделано). Фронт считает её сам.
