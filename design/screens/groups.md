# Группы

Макет: `design/screens/groups.html`. Панель в правом верхнем углу переключает состояния: данные, загрузка, пусто, ошибка, окно «Изменить», окно «Новая группа» (с ошибками), окно удаления, тема. Во фронтенд панель не переносить.
Компоненты и форматы описаны в `design/system.md`, значения берутся из `design/tokens.css`, эталонная вёрстка — `design/components.css`.

Маршрут: `/groups`.

## Назначение
Настроить области жизни (учёба, работа, дом) и их вес. Вес группы — множитель `Pg` в формуле приоритета, поэтому здесь пользователь управляет тем, какие задачи окажутся выше. Сюда же приходят, чтобы переименовать или удалить группу.

## Как попасть на экран (решение)

- **Мобильный: icon-кнопка «Группы» (иконка папки) в `AppHeader` экрана «Все задачи»**, перед аватаром. На экране «Группы» `BottomNav` остаётся с активным пунктом «Все задачи», «назад» ведёт на `/all-tasks`.
- **Десктоп: пункт «Группы» в `SideNav`** под «Все задачи».
- Дополнительно: ссылка «Управлять группами» под `GroupPicker` на экранах «Новая задача» и «Задача».

Почему так:
- Группы — это структура экрана «Все задачи»: там задачи разложены по группам с весом «×3». Настройка групп рядом с местом, где видно её последствия, понятнее всего.
- Нижняя навигация в концепции автора — два главных экрана «День» и «Все задачи». Группы настраивают редко (при старте и изредка потом). Третий пункт отнимал бы место у ежедневных действий и размывал бы простую схему.
- В профиле групп не ищут: профиль про пользователя (а он пока заглушка без данных). Кроме того, путь через профиль — лишний шаг.
- На десктопе в `SideNav` места достаточно, и отдельный пункт делает группы видимыми без лишнего клика.

Изменения в других экранах: `design/screens/all-tasks.html` (кнопка в шапке и пункт `SideNav`), `design/screens/day.html` (пункт `SideNav`), `system.md` → «Карта экранов и навигация», `AppHeader`, `SideNav`.

## Данные

`userId` — `CURRENT_USER_ID`. Все пути с префиксом `/api`. Ответы — PascalCase, запросы — camelCase.

Загрузка — два параллельных запроса (оба уже в кэше, если пользователь пришёл с «Все задачи»):
1. `GET /api/groups/user/:userId` → `Group[]` (кэш `queryKeys.groups`). Старый ответ 404 «Группы пользователя не найдены» трактовать как `[]` (уже сделано в `fetchUserGroups`).
2. `POST /api/tasks/user/:userId`, тело `{}` → `Task[]` (кэш `queryKeys.tasks`): для счётчиков. Считаем по `Task.GroupId`, как на «Все задачи», а не по `Group.Tasks`, чтобы числа совпадали. Если этот запрос упал, счётчики берутся из `Group.Tasks` (приходит в ответе групп через preload), а строка «Без группы» скрывается.

| Что показываем | Источник | Поле | Формат |
|---|---|---|---|
| Вес группы | `GET /api/groups/user/:userId` | `Group.GroupPriority` | `WeightTile` «×3» |
| Название | то же | `Group.Name` | одна строка, многоточие |
| Счётчик задач | `POST /api/tasks/user/:userId` | число задач с `Task.GroupId = Group.GroupId`, из них со `Status = 2` | «4 задачи · 1 выполнена»; без выполненных — «3 задачи»; 0 — «Нет задач» |
| Порядок | то же | `GroupPriority` ↓, затем `Name` (как секции на «Все задачи») | после изменения веса строка переезжает на новое место (FLIP-анимация, `useFlip`) |
| «Без группы» | `POST /api/tasks/user/:userId` | задачи с `GroupId = 0` или без существующей группы | отдельная некликабельная карточка «Без группы · N задач · вес всегда ×1»; не показывается, если таких задач нет |
| Задачи, которых коснётся изменение | то же | задачи группы со `Status = 1` | число в подсказке `GroupForm` и в `ConfirmSheet` удаления |

`Group.Description` на экране не показывается и не редактируется: в интерфейсе оно нигде не используется.

## Компоненты

Из `system.md`: `AppShell` (с `BottomNav`, активный пункт «Все задачи»), `SideNav` (активный «Группы»), `PageHeader` с ghost-действием «Новая группа», `GroupList` / `GroupRow`, `WeightTile`, `Sheet` + `GroupForm` (Stepper веса), `ConfirmSheet`, `Alert`, `Button` (ghost, danger-ghost, danger, загрузка), `Skeleton`, `EmptyState`, `ErrorState`, `Toast`.

Новые для этого экрана: `GroupRow`/`GroupList`, `WeightTile`. Общие с экранами задачи: `PageHeader`, `GroupForm`, `ConfirmSheet`, `Alert`.

Структура сверху вниз:
1. `PageHeader`: «назад» (→ `/all-tasks`), «Группы», справа ghost «+ Новая группа».
2. Пояснение (`page-intro`, `--text-sm` muted): «Вес группы умножает приоритет всех её задач: задача из группы ×3 при прочих равных встанет выше задачи из группы ×1.»
3. `GroupList` со всеми группами.
4. Карточка «Без группы».
5. `BottomNav`.

На этом экране нет `Fab`: он везде означает «новая задача», и здесь сбивал бы с толку. Создание группы — ghost-кнопка в шапке и primary-кнопка в пустом состоянии.

**Текст подтверждения удаления:**
- в группе есть задачи: «N задач группы не удалятся — они перейдут в „Без группы“, и их приоритет пересчитается с весом ×1» + если вес группы > 1: «, то есть станет в K раз ниже» (K = вес группы);
- задач нет: «В группе нет задач».

### Что происходит с задачами при удалении группы (по коду бэкенда)

`GroupServiceImpl.DeleteGroup` (`internal/services/group_services.go`) и `GroupRepositoryImpl.DeleteDetachingTasks`:
1. Находит все задачи группы по `Task.GroupId`, любого статуса.
2. Каждой задаче ставит `GroupId = 0`, `GroupPriorty = 1` и пересчитывает `Priority` по формуле (у выполненных он остаётся 0).
3. В одной транзакции сохраняет эти поля задач и удаляет группу. Связи в `group_tasks` удаляются каскадом.
4. **Задачи не удаляются** и остаются в планах дней (`day_tasks` не трогается). `Day.PriorityOfTheDay` в БД не пересчитывается, но фронт считает остаток приоритета дня сам по `Tasks`, поэтому после инвалидации `days` цифры будут верными.

### Что происходит при изменении веса (по коду бэкенда)

`GroupServiceImpl.UpdateGroup`: при `groupPriorty > 0` для каждой задачи группы вызывается `TaskService.UpdateTask` с новым `GroupPriority`. У задачи обновляется `GroupPriorty` и пересчитывается `Priority`. Переименование задачи не затрагивает.

## Адаптивность

- < 960px: как в макете. `BottomNav` с активным «Все задачи». Кнопка «Новая группа» в шапке — ghost с иконкой и текстом (на ширине < 360px — только иконка «+» с `aria-label="Новая группа"`). `Sheet` выезжает снизу.
- ≥ 960px: `SideNav` с активным «Группы», `BottomNav` скрыт, колонка до 720px, строки групп с hover. `Sheet` — диалог 420px по центру.

## Требуется от бэкенда

1. **Опечатка в ключе веса.** `GroupUpdateRequest.GroupPriority` имеет тег `json:"groupPriorty"`, а `GroupCreateRequest` — `json:"groupPriority"`. Фронт вынужден отправлять разные ключи. Предложение: принимать `groupPriority` (и временно оба ключа), затем удалить опечатку синхронно с фронтом.
2. **Изменение веса неатомарно и медленно.** `UpdateGroup` обновляет задачи по одной через `UpdateTask` (N запросов, без транзакции). Если упадёт посередине, у части задач будет старый вес. Нужна одна транзакция (обновить `group_priorty` и `priority` задач группы и саму группу).
3. **Удаление через `DELETE /api/groups/:id`**, как планировалось. Сама логика отвязки задач уже подходит экрану.
4. **Уникальность названия.** Сервер позволяет создать две группы «Учёба». Фронт проверяет по загруженному списку, но нужна проверка и на сервере: 409 «Группа с таким названием уже есть», с учётом trim и регистра.
5. **Границы веса.** Сейчас принимается любой `uint64 ≥ 1`. Предложение: валидировать 1–10 (`binding:"min=1,max=10"`), чтобы один вес не «съедал» всю шкалу приоритетов. Нужно решение автора.
6. **Счётчики вместо полного preload.** `GET /api/groups/user/:user_id` отдаёт каждую группу с полным массивом `Tasks`. Для этого экрана достаточно `TaskCount` и `DoneCount`. Сейчас фронт считает сам по списку задач, так что это оптимизация, а не блокер.
7. **Коды ответов.** `POST /api/groups/` отвечает 200 (для создания ожидается 201). `GET /api/groups/:id` на несуществующую группу отвечает 500 «нет записи с таким ID» вместо 404. Экран не использует `GET /api/groups/:id`, но для единообразия стоит поправить.
8. **Очистка описания.** `description: ""` в update игнорируется. Экран описание не использует, пункт на будущее.
